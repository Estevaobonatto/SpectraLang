Relatório completo · suporte a POO

A linguagem já tem objetos sem ter classes

A SpectraLang já entrega um núcleo de POO orientado a tipos, composição e contratos. O caminho implementado se parece muito mais com Rust do que com Java ou Python: dados em struct, comportamento em impl, polimorfismo em trait e despacho dinâmico em dyn Trait.

O núcleo é suficiente para encapsulamento, composição, interfaces, polimorfismo estático e dinâmico e operadores definidos por traits.

Não é ainda um sistema de classes, herança de implementação ou propriedades.

01 · leitura rápida

A pergunta certa não é “há classes?”

A pergunta útil é se a linguagem permite modelar estado, comportamento, contratos, encapsulamento, reutilização e polimorfismo com uma semântica coerente. Hoje, a resposta é sim para o modelo baseado em traits e não para a POO clássica baseada em classes.

Conclusão em uma frase

A SpectraLang já possui uma base de POO funcional e interessante, mas precisa assumir explicitamente que seu paradigma principal é composição com traits ou então projetar, de ponta a ponta, uma camada de classes que hoje ainda não existe.

02 · arquitetura do paradigma

O caminho implementado é uma cadeia de composição

O estado fica separado do comportamento. Um tipo pode cumprir vários contratos sem herdar dados de outro tipo. Quando o programa precisa de abstração dinâmica, o compilador produz um objeto gordo com ponteiro de dados e tabela de métodos.

Despacho estático · T: Trait

A semântica resolve o método a partir dos limites genéricos e o midend especializa o caminho conforme o tipo concreto.

Despacho dinâmico · dyn Trait

04 · rastreabilidade

Onde cada parte do paradigma vive

A POO atual não está apenas aceita pelo parser. Há registro no AST, regras semânticas, lowering de chamadas e suporte de backend para o caminho dinâmico.

Lexer e parser

O frontend reconhece o vocabulário trait-first e organiza os blocos com chaves.

  • struct, enum, impl, trait, Self e dyn têm caminho de token e parse
  • receivers self, &self e &mut self são representados
  • class aparece como palavra reservada e ponto de recuperação, não como item
abrir parser de itens

AST e contratos

O AST tem nós separados para comportamento próprio e implementação de trait.

  • Item::Struct, Item::Enum, Item::Impl, Item::Trait e Item::TraitImpl
  • TraitMethod pode ter assinatura ou corpo default
  • não existe ClassDecl, override ou membro associado de trait
abrir AST

Análise semântica

A análise registra métodos por tipo e valida a relação entre contrato e implementação.

  • assinaturas, retorno, aridade, receivers e duplicidade
  • traits pais, defaults, bounds, visibilidade e chamadas em dyn Trait
  • regra dedicada para object safety async com diagnóstico E2108
abrir semântica

Midend e backend

O despacho dinâmico tem representação concreta no caminho de geração.

  • método direto vira chamada com receiver como primeiro argumento
  • dyn Trait usa ponteiro de dados e ponteiro de vtable
  • o backend carrega o slot e emite CallIndirect
abrir lowering · abrir backend
Inconsistência documental que precisa ser corrigida

docs/semantic/semantic-coverage-audit.md classifica declarações de classe como parciais e a política de maturidade chama o footprint de classe de beta. Na implementação viva, o parser não tem ramo para declarar uma classe e o AST não tem item correspondente. O status técnico correto hoje é “palavra reservada sem suporte de linguagem”, até que um pipeline completo seja criado.

05 · fronteiras atuais

O que falta para chamar o suporte de completo

Algumas ausências são deliberadas no modelo Rust-like. Outras são lacunas de implementação ou de contrato que precisam ser resolvidas mesmo se a linguagem continuar sem classes.

RecursoStatusDiagnóstico atualImpacto
Declaração de classeausente

class é reservado no lexer, mas não existe parse, AST, semântica, lowering ou backend de classe.

Não há sintaxe de classe executável.

Herança de implementaçãoausente

Traits pais herdam contratos. Nenhum tipo herda campos e métodos concretos de uma classe base.

Não existe substituição baseada em hierarquia de objetos.

Construtor da linguagemconvenção

fn new, open e create são funções associadas. O compilador não injeta inicialização.

Invariantes precisam ser mantidas pela API.

Propriedades e acesso controladoausente

O modelo usa campos e métodos. Não há sintaxe declarativa para propriedade calculada, leitura ou escrita controlada.

Getters e mudança de estado são métodos explícitos.

protected e acesso de famíliaausente

A política atual é pública, interna ou privada. Não existe visibilidade para subclasses.

Encapsulamento é por módulo e tipo.

Sobrecarga de métodosausente

O registro semântico usa o nome por tipo e acusa duplicidade. Não há seleção por assinatura.

APIs precisam de nomes distintos ou traits distintos.

override, abstract, final e superausente

Defaults de trait podem ser substituídos, mas não há palavras de controle para hierarquia clássica.

Não há override nominal ou bloqueio de extensão.

Tipos e constantes associadosausente

O AST e o parser de trait registram métodos. Não há itens equivalentes a type Item ou constantes associadas.

Limita abstrações genéricas mais expressivas.

Identidade e reflexãofora do contrato

Não há contrato de this, identidade observável, RTTI, reflexão de membros ou coleta de lixo orientada a objetos.

O modelo favorece valores e contratos estáticos.

Drop de campos aninhadosnão certificado

O lowering registra structs com Drop e chama o destrutor ao sair. O exemplo com TempFile falhou antes de completar o cenário aninhado.

Recursos exigem uma matriz de saídas, branches e campos.

Tooling e documentaçãoprecisa alinhar

Há indexação de impls e traits, mas a documentação mistura footprint de classe com suporte real.

O usuário pode esperar uma linguagem de classes que o compilador não aceita.

06 · paralelo de linguagem

Rust é o paralelo correto para o que existe hoje

Rust não usa classes tradicionais. Ele usa structs, impls, traits e objetos de trait. A comparação mede coerência do caminho atual sem exigir uma herança clássica que nunca foi implementada.

Leitura arquitetural

A SpectraLang está mais próxima de Rust do que de Java, C# ou Python. A principal diferença não é a existência de classes. É o grau de completude dos contratos, dos tipos associados, do object safety, do ciclo de vida e do tooling.

Nota sobre POOEm Rust, composição, encapsulamento, abstração e polimorfismo também são POO. A ausência de uma palavra class não impede o paradigma.

08 · plano recomendado

Recomendações para tornar a POO coerente e adotável

A prioridade não deve ser adicionar palavras clássicas por aparência. Primeiro é preciso fechar o contrato do modelo já escolhido. Uma camada de classes só deve entrar se houver necessidade de produto clara.

P0

Declarar oficialmente o modelo trait-first

Tratar struct + impl + trait como a forma oficial de POO. Explicar que isso cobre encapsulamento, abstração, composição e polimorfismo sem classes.

  • revisar a política de maturidade para não chamar class de beta
  • mover classe para reservado ou deferred até existir um pipeline real
  • documentar herança de trait como herança de contrato
ResultadoMenos ambiguidade para quem aprende e menos risco de misturar dois paradigmas.
P0

Fechar o ciclo de vida de Drop

O reconhecimento semântico e o lowering já existem, mas o exemplo integrado não completou a execução. Transformar o ciclo de vida em contrato testado.

  • cobrir saída normal, retorno antecipado, branches e loops
  • definir ordem entre variáveis e campos aninhados
  • corrigir e executar novamente o exemplo de Drop
ResultadoRecursos como arquivos e conexões deixam de depender de uma promessa não certificada.
P0

Formalizar o contrato de dyn Trait

Manter a vtable e completar a especificação de quando um trait pode virar objeto, como auto traits entram e quais receivers são aceitos.

  • ampliar object safety além da regra específica para async
  • documentar coerção, armazenamento, chamada e conversão
  • adicionar diagnostics para métodos indisponíveis no objeto
ResultadoPolimorfismo dinâmico previsível para APIs, plugins e drivers.
P1

Adicionar itens associados a traits

Incluir tipos e constantes associados. Esse é o maior gap estrutural em relação a Rust para abstrações genéricas expressivas.

  • começar com tipo associado simples e resolução em impl
  • validar conflitos, bounds e uso em funções genéricas
  • adicionar constantes associadas após o tipo estar estável
ResultadoTraits passam de contratos apenas de métodos para famílias de tipos.
P1

Padronizar fábricas e encapsulamento

Manter funções associadas livres, mas criar convenção para new, open, from, validação e falha de construção.

  • documentar invariantes e campos privados
  • preferir métodos quando o campo não deve ser exposto
  • explicar que não existe protected por escolha de módulo
ResultadoAPIs legíveis sem inventar semântica de classe incompleta.
P1

Fortalecer diagnostics e tooling OOP

A infraestrutura já indexa impls e traits. O próximo passo é tornar erros de contrato fáceis de corrigir no editor.

  • mostrar trait exigido, método faltante e assinatura encontrada juntos
  • oferecer go-to-definition entre método de trait e implementação
  • exibir no hover o tipo de método e a forma de dispatch
ResultadoA POO fica ensinável e produtiva, não apenas compilável.
P2

Adicionar classes apenas como decisão separada

Se o produto exigir POO clássica, não transformar class em açúcar superficial para struct. Projetar um segundo modelo completo.

  • definir campos de base, dispatch virtual, herança, acesso e inicialização
  • especificar override, método abstrato, final e chamada ao pai
  • definir ABI, layout, ownership, destruição e integração com traits
ResultadoSomente iniciar se houver casos que justifiquem duas semânticas de objeto.
P2

Deixar reflexão e identidade fora do núcleo

Não adicionar recursos de linguagens de classes por completude estética. Eles podem ser bibliotecas ou extensões futuras.

  • preferir traits de conversão e debug a reflexão implícita
  • preferir IDs explícitos quando identidade for necessária
  • avaliar propriedades após observar repetição real em APIs
ResultadoO núcleo continua pequeno e compatível com dados, API e ML.

09 · decisão de produto

Duas rotas possíveis, uma recomendação

recomendado

Consolidar o modelo Rust-like

Assumir que POO na SpectraLang significa tipos com comportamento, traits como contratos e objetos dinâmicos quando necessário.

  • preserva o que já funciona
  • evita duplicar regras de herança e ownership
  • combina com dados, concorrência, API e ML
  • permite remover a ambiguidade de class
somente se necessário

Criar uma camada clássica de classes

Implementar um sistema próprio para usuários que precisem de hierarquia nominal, estado herdado e dispatch virtual orientado a classe.

  • exige novos nós de AST e regras semânticas
  • exige layout, ABI, lifecycle e compatibilidade com traits
  • exige tooling, diagnostics e documentação próprios
  • não pode ser anunciado como concluído com apenas um token

Validação realizada durante esta análise

O parser test filter passou com 10 testes e o gate semantic filter passou com 1 teste. O lowering test filter passou com 2 testes. No binário local target/debug/spectralang.exe, executaram com código zero os exemplos de encapsulamento, dyn trait, operadores e casting. O exemplo de Drop encerrou com código 1 logo após a primeira abertura de Buffer, por isso este relatório não declara o ciclo de vida como totalmente certificado.

veredito final

A POO já é real. A POO clássica ainda não.

O investimento de maior retorno é consolidar o modelo que a implementação já demonstra, fechar Drop e object safety, adicionar itens associados e alinhar a documentação. Se classes forem necessárias, elas devem entrar como projeto de linguagem completo, não como palavra reservada com status beta.
